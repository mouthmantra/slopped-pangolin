# Forking and distributing Pangolin

This is a practical guide to publishing a fork of Pangolin (the desktop, the
dahliaOS apps and the modified river compositor) on GitHub, and to shipping
it as binaries or distribution packages. It summarizes the licenses in this
tree and what they ask of you.

> This guide is not legal advice. It reflects the licenses as they are found
> in this repository; if you build a product or company on top of it, have a
> lawyer read the actual license texts.

## What is in the tree, under which license

| Part | Where | License |
| --- | --- | --- |
| Pangolin shell, session scripts, tools | `lib/`, `linux/`, `session/`, `tool/` | Apache-2.0 (`LICENSE`) |
| dahliaOS apps (Settings, Files, App Store, Terminal, ...) | `apps/` | Apache-2.0 |
| Pangolin packages: `wayland`, `display_config`, `system_controls`, `pangolin_settings` | `packages/` | Apache-2.0 |
| Zenit UI | `packages/zenit_ui/` | Apache-2.0 (`packages/zenit_ui/LICENSE`, as upstream [dahliaOS/zenit_ui](https://github.com/dahliaOS/zenit_ui)) |
| Inter font | `packages/zenit_ui/lib/src/fonts/` | SIL Open Font License 1.1 (`OFL.txt` next to the fonts) |
| river, with Pangolin's changes | `river-main/river/` | GPL-3.0-only for the code; MIT for its Wayland protocols; CC-BY-SA-4.0 for its logo and documentation; some files 0BSD. Each file says which (REUSE: SPDX headers, texts in `river-main/river/LICENSES/`). |
| Papirus icons (Files' file and folder icons only) | `apps/assets/papirus/` | GPL-3.0 (`apps/assets/papirus/LICENSE`), from [PapirusDevelopmentTeam/papirus-icon-theme](https://github.com/PapirusDevelopmentTeam/papirus-icon-theme); the commit is in `apps/assets/papirus/README.md`, `tool/papirus_icons.py` copies them |
| Pointer theme | generated by `tool/cursors/` | Apache-2.0 (drawn by our own code), except the hand cursors, which are GNOME's Adwaita ones: CC-BY-SA-3.0-US (or LGPL-3.0), see `tool/cursors/adwaita/README.md` |
| Wallpapers, logos, `CustomIcons.ttf` | `assets/`, `apps/assets/` | Came with upstream [dahliaOS/pangolin_desktop](https://github.com/dahliaOS/pangolin_desktop) (Apache-2.0). The dahliaOS and Pangolin logos are also the project's trademarks, see below. |
| Dart/Flutter dependencies | `pubspec.yaml` files | Their own licenses (BSD, MIT, Apache-2.0). From git: `dahliaOS/shared`, `dahliaOS/utopia`, `dahliaOS/dsettings` (Apache-2.0), `HrX03/yatl`, `HrX03/xdg.dart` (MIT), the `cached_network_image` fork (MIT). |
| Flutter engine and framework | linked into the shell and apps bundles | BSD-3-Clause, plus the third party notices Flutter collects |

Every license above allows forking, modifying and redistributing, also
commercially. What differs is what you must ship along.

## What each license asks of you

**Apache-2.0** (most of Pangolin):

- Keep the `LICENSE` file and the copyright and license headers in the
  files.
- Files you change must say they were changed (a line in the header, or
  your git history published with the source, is the usual way).
- Your own new files can use any license compatible with Apache-2.0; add
  your copyright line.
- It gives you no rights to the dahliaOS names and logos (section 6).
- If a `NOTICE` file exists upstream you must carry it along. There is none
  today.

**GPL-3.0-only** (river):

- Whoever gets the `river` binary from you must be able to get its complete
  corresponding source: the exact `river-main/river` tree it was built from,
  with the build files. Publishing the binaries as assets of a GitHub release
  whose tag contains that tree does it (GitHub attaches the tag's source
  archive to the release).
- Keep its license texts (`river-main/river/LICENSES/`) and copyright
  notices, and mark your changes with a date (SPDX headers plus the git
  history).
- Your changes to river are GPL-3.0-only too, whatever the rest of Pangolin
  uses. Keep river changes in `river-main/river/` so the line stays clear.
- Shipping river on hardware you sell (a laptop with Pangolin preinstalled)
  also requires the installation information to replace it (GPLv3 section
  6). Not relevant for downloads.

**The shell and river are separate programs.** Pangolin's shell talks to
river through Wayland protocols, as any Wayland client does; the GPL of
river does not extend to the shell, and Apache-2.0 code may be distributed
next to GPL-3.0 code (they are compatible). Do not copy river's GPL code
into the shell (or the other way around) unless you are fine with the result
being GPL-3.0.

**MIT, BSD, 0BSD:** keep the copyright and license text with the code and,
for binaries, in the documentation or notices shipped with them.

**SIL OFL 1.1** (Inter): ship `OFL.txt` with the fonts. You may bundle the
fonts with any software; if you modify the fonts themselves, the "Inter"
name may not be used for the modified fonts.

**GPL-3.0** (Papirus icons): the icons are data the Files app loads, not
code linked with it; ship their license (`apps/assets/papirus/LICENSE`) and
say where they come from. Changed icons stay GPL-3.0, and their sources
(the SVGs themselves) go with them.

**CC-BY-SA-4.0** (river's logo and documentation): only matters if you use
them; credit river and share changes alike.

**CC-BY-SA-3.0** (Adwaita's hand cursors in the pointer theme): keep the
attribution to the GNOME Project and the license link
(`tool/cursors/adwaita/README.md`); changed versions of those cursors must
be shared under the same license.

## Binaries already carry most notices

- `flutter build linux` puts the licenses of Flutter and of every Dart
  package into the bundle (`data/flutter_assets/NOTICES.Z`), shown by the
  apps' "About" / licenses pages.
- `tool/install.sh` installs the license texts that are not in those
  notices (Apache-2.0, river's licenses, Inter's OFL) to
  `share/licenses/pangolin/`, where distributions keep license files.
- `dsettingsd` and `pangolin-displays` are compiled Dart programs without
  bundled notices: their dependencies are the same Dart packages the shell
  uses, whose notices the shell's bundle carries. If you ship them alone,
  ship `share/licenses/pangolin/` with them.

## Names and logos

"dahliaOS", "Pangolin" and their logos identify the dahliaOS project. The
code licenses don't cover them:

- A fork that is published as something else should get its own name and
  logo, and say where it comes from ("based on Pangolin from dahliaOS"),
  which is welcome and true.
- Keeping the names for an unofficial build (e.g. a package of upstream
  Pangolin for your distribution) is common practice, but ask the dahliaOS
  maintainers if it could be mistaken for an official release.
- The About page of Settings shows the distribution's own logo and name
  (from `/etc/os-release`): a distribution shipping Pangolin keeps its
  branding without patching anything.
- To rebrand, the places to look at are `assets/images/logos/`,
  `apps/assets/images/`, the app icons in `session/icons/`, the session
  name in `session/wayland-sessions/pangolin.desktop.in` and the window
  titles.

## Checklist for a fork on GitHub

1. Fork, keep `LICENSE`, the headers and `river-main/river/LICENSES/`.
2. Say in the README what the fork is, what it is based on and under which
   licenses (you can link to this file).
3. Commit your changes with clear messages: the published history is your
   record of changes for Apache-2.0 and GPL-3.0.
4. For a release: tag it, build from the tag (`tool/build.sh`), attach the
   build to the GitHub release of that tag. Its source archive is the
   corresponding source of the river binary in it.
5. Put the license texts in the archive you attach (`tool/install.sh
   --prefix <staging dir>` does, under `share/licenses/pangolin/`).
6. Leave the dahliaOS logos out of anything that looks official unless you
   asked (see above).
7. Optional but useful: `reuse lint` (https://reuse.software) checks that
   every file says its license; river already passes.

## For distribution packages

`tool/dist.sh` makes the source tarball (river's Zig dependencies included,
build outputs left out) and `tool/install.sh --prefix /usr --destdir DIR`
stages an installation for a package. `packaging/rpm/` has a Fedora spec
(`tool/rpm.sh` builds it): the system parts an install script would do by
hand (the login screen's user, PAM, greetd and logrotate configuration) are
package files there (sysusers.d, tmpfiles.d, a greetd.service drop-in).

An SPDX license expression for a package containing everything built here:

```
Apache-2.0 AND GPL-3.0-only AND MIT AND BSD-3-Clause AND OFL-1.1 AND CC-BY-SA-3.0
```

A distribution may also split it: `river-pangolin` (GPL-3.0-only AND MIT),
`pangolin` (Apache-2.0 AND BSD-3-Clause AND MIT AND OFL-1.1) and
`dahlia-apps` (Apache-2.0 AND BSD-3-Clause AND MIT AND OFL-1.1).

Runtime dependencies (not bundled, the distribution provides them) keep
their own licenses: wlroots (MIT), GTK 3 (LGPL-2.1-or-later), libwayland
(MIT), PAM, polkit, PackageKit, PipeWire and the xdg-desktop-portal
implementations. Linking them dynamically, as the build does, asks nothing
more of you.
